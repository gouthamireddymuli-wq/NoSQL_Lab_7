1. Embedding vs Referencing Decision Framework

The fundamental rule of MongoDB data modeling is: Data that is accessed together should be stored together. However, unbounded array growth can violate MongoDB's 16 MB maximum document size limit.

When to EMBED (Denormalize)

  • 1:1 Relationships: Threat report metadata, primary author details.
  • 1:Few Relationships (< 20 items): MITRE ATT&CK technique tags, affected CVE IDs.
  • Atomic Updates: Need to update parent and child attributes in a single atomic disk write.
  • High Read Throughput: Avoids application-level roundtrips or $lookup joins.

When to REFERENCE (Normalize)

  • 1:Squillions: Continuous firewall packet logs or IoT sensor telemetry.
  • Many-to-Many (N:M): Threat Actors operating across thousands of dynamic IP observables.
  • Independent Lifecycles: Entities updated frequently by independent pipelines.
  • Prevent 16 MB Cap Exceeded: Eliminates runaway unbounded array anti-patterns.

2. Server-Side Integrity via $jsonSchema Validation 

db.create_collection("threat_indicators", validator={
    "$jsonSchema": {
        "bsonType": "object",
        "required": ["type", "value", "confidence", "platform"],
        "properties": {
            "type": {"enum": ["ip", "domain", "sha256", "cve", "url"]},
            "value": {"bsonType": "string"},
            "confidence": {"bsonType": "int", "minimum": 0, "maximum": 100},
            "platform": {"enum": ["Linux", "Windows", "MacOS", "Android", "iOS", "Cloud"]}
        }
    }
})
