Lab 8.1

Deploy Local Replica Set

Objective & Setup

Lab 8.1 deploys a 3-node MongoDB Replica Set (rs0) using Docker Compose on ports 27017, 27018, and 27019. A replica set is a group of mongod processes that maintain the same dataset, providing redundancy and high availability.

rs.initiate() Explained

rs.initiate() bootstraps a replica set by sending a configuration document to the primary candidate. MongoDB negotiates an election and elects the member with the highest priority as PRIMARY. Once initiated, the replica set begins continuous oplog replication between all members.

Member Roles

  • PRIMARY — Receives all write operations; replicates to secondaries via the oplog.
  • SECONDARY — Replicates data from primary; can serve reads if explicitly enabled.
  • ARBITER — Votes in elections only; stores no data, requires minimal resources.
Docker Compose Setup: Three mongo:7 containers share a bridge network (rs0_net). Persistent volumes (rs0_data1/2/3) ensure data survives container restarts. Each container receives --replSet rs0 as a startup flag, telling MongoDB which replica set it belongs to. After containers are healthy, init_replicaset.js is executed via mongosh to call rs.initiate().

Arbiter Node

Understanding the Arbiter Role

With Arbiter (2 data nodes + 1 arbiter) Without Arbiter (2 data nodes only)
Majority quorum = 2 out of 3 votes → elections always succeed Majority quorum = 2 out of 2 → one failure = no quorum, no election
Arbiter uses near-zero RAM/CPU (no data storage) Third node must be a full data-bearing replica (+RAM +storage cost)
Tie-breaking vote prevents split-brain in network partition Split-brain: both nodes see themselves as isolated, writes blocked
Failover completes even if one data node is offline Loss of any node causes the remaining node to step down
Ideal for resource-constrained environments (IoT, dev labs) All members must have identical storage capacity
Key Configuration: arbiterOnly: true
Setting arbiterOnly: true tells MongoDB this member participates in elections with 1 vote but never stores user data. It cannot be elected PRIMARY and does not replicate the oplog.

Arbiter Init Configuration (port 27020):

rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "host.docker.internal:27017", priority: 2 },
    { _id: 1, host: "host.docker.internal:27018", priority: 1 },
    { _id: 2, host: "host.docker.internal:27020", arbiterOnly: true }
  ]
})

Why Arbiters Are Useful

In distributed systems, reaching a decision requires a majority of votes. MongoDB's election protocol uses the Raft consensus algorithm, where a node needs ⌊N/2⌋ + 1 votes to be elected PRIMARY. With only two data-bearing nodes, neither can achieve a majority if the other is unreachable — causing the entire replica set to become read-only. An arbiter solves this by providing the decisive third vote without the storage and memory overhead of a full data node.

Consider a scenario where your infrastructure budget limits you to two powerful database servers. Adding a third full replica would triple your storage costs. Instead, you can run an arbiter on a cheap VM or even a Docker container on the application server. The arbiter consumes under 1 MB of RAM, requires no disk space for data, and contributes exactly one vote — the same as any data-bearing node — to election quorum. This is why arbiters are extremely popular in cost-sensitive deployments.

The arbiter also protects against split-brain scenarios. In a network partition where two data nodes can no longer communicate, each node might believe itself to be the only surviving member and attempt to accept writes independently, creating divergent datasets. With an arbiter in a third network zone (or even on the application server), the arbiter's vote prevents any isolated single node from claiming majority, forcing the system into a safe read-only state rather than allowing a dangerous split-brain.

One important caveat: an arbiter with arbiterOnly: true cannot serve reads. Attempting to query it directly will raise an error because it holds no collection data. Its sole purpose is voting. This makes it fundamentally different from a SECONDARY, which can be configured to serve reads with readPreference: "secondaryPreferred". Understanding this distinction is critical for correctly routing application traffic in a 2-data-node + arbiter topology.

activity_8_2.py Key Functions

get_primary(client) — Detect current primary

def get_primary(client):
    """Returns the current primary host string from rs.status()."""
    status = client.admin.command("replSetGetStatus")
    for member in status["members"]:
        if member["stateStr"] == "PRIMARY":
            return member["name"]
    return None

monitor_replica_set(duration, interval) — Poll & detect failover

def monitor_replica_set(duration=90, interval=2):
    client = MongoClient(RS_URI)
    start = time.time()
    last_primary = get_primary(client)

    with open("failover_log.txt", "w") as log:
        while time.time() - start < duration:
            current_primary = get_primary(client)
            ts = datetime.now().strftime("%H:%M:%S")

            if current_primary != last_primary:
                msg = f"*** FAILOVER DETECTED: {last_primary} → {current_primary} ***"
                print(f"\033[91m{msg}\033[0m")
                log.write(msg + "\n")
                last_primary = current_primary

            # Print all member states
            status = client.admin.command("replSetGetStatus")
            for m in status["members"]:
                line = f"[{ts}] {m['name']} → {m['stateStr']}"
                print(line)
                log.write(line + "\n")

            time.sleep(interval)

continuous_read_demo(duration, interval) — Read during failover

def continuous_read_demo(duration=60, interval=1):
    client = MongoClient(RS_URI, read_preference=ReadPreference.PRIMARY_PREFERRED)
    col = client.testdb.replication_test
    start = time.time()

    while time.time() - start < duration:
        try:
            doc = col.find_one(sort=[("_id", -1)])
            host = client.address
            print(f"  → Read from {host}: {doc.get('label') if doc else 'empty'}")
        except ConnectionFailure as e:
            print(f"  [ConnectionFailure] Reconnecting... {e}")
        time.sleep(interval)

MongoDB Election Algorithm Explained

MongoDB replica set elections are governed by a modified version of the Raft consensus protocol. When the current primary steps down — either voluntarily via rs.stepDown() or due to a network failure — all eligible secondaries transition to a SECONDARY state briefly and then one or more candidates initiate an election by incrementing the election term and requesting votes from peers.

Priority and election score: Each member has a configured priority value (default: 1). A higher priority member will veto a lower-priority candidate's victory if the high-priority member is eligible (i.e., its oplog is sufficiently up to date). MongoDB calculates an election "score" that incorporates both priority and oplog recency, ensuring the most qualified member wins rather than simply the fastest to call an election.

Priority = 0 means never primary: Any member with priority: 0 is permanently ineligible to become PRIMARY. It can still vote in elections, replicate data, and serve reads (if secondaryOk is set), but it will never initiate an election or accept a vote for itself. This is used for dedicated reporting nodes, geographically distant replicas, and hidden members that should not attract write traffic.

Oplog recency requirement: Even the highest-priority member cannot win an election if its oplog lags too far behind. MongoDB requires that the winning candidate's oplog timestamp (the lastApplied OpTime) is no more than a configurable threshold behind the most advanced member's oplog. This prevents a restarted secondary that missed many writes from becoming primary and potentially losing data. In this activity, since all three nodes are on the same host with no artificial lag, the highest-priority node (:27018, priority=3) will reliably win every election.
