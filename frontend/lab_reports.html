Lab 7.1

Analyze a Production Schema (CTI Platform — ctidigest.com)

1. Embedding vs Referencing Decisions in CTI Production Schema

In modeled production systems based on CTI Digest, threat intelligence documents combine high write/update volume (sighting telemetry) with complex entity graphs (threat actors, malware families, campaigns). Here is the relationship breakdown:

Relationship Pattern Cardinality Rationale
Indicator → Sources EMBEDDED 1 : Few (1–10) Telemetry feeds (AlienVault, MISP, Honeypot) are always inspected together with the indicator value. Bounded array prevents unbounded growth.
Indicator → MITRE ATT&CK EMBEDDED 1 : Few TTP codes (e.g. T1566, TA0001) are standardized static strings. Stored directly inside attribution.mitre_attack for zero-join querying.
Indicator → Context Data EMBEDDED 1 : 1 Type-specific technical data (e.g. SHA256/MD5 for files, ASN/Country for IPs) belongs strictly to that single indicator document.
Indicator → Threat Actors REFERENCED N : M Threat actor dossiers (biographies, nation-state attribution, history) are heavy (5–20 KB) and shared across thousands of indicators. References via actor_id.
Report → Related Indicators REFERENCED N : M An intelligence bulletin mentions 10–50 indicators; an indicator can appear across 100+ bulletins over its lifetime. References via related_indicators: [indicator_id].

2. Referencing Rationale & Embedded Alternatives

Relationship 1: Indicator → Threat Actor

Why Embedding was NOT used:
Threat actors (e.g., APT29, LockBit) mutate independently of indicators. If full dossiers were embedded inside every indicator, adding a newly identified tool or alias would trigger massive write amplification (updating 50,000+ indicator records across disk and indexes).

Embedded Alternative Schema: 
{
  "indicator_id": "ind-003",
  "value": "194.165.16.11",
  "threat_actor": {
    "actor_id": "actor-001",
    "name": "Cozy Bear",
    "aliases": ["APT29", "Midnight Blizzard"],
    "country": "Russia",
    "motivation": "Espionage",
    "ttps": ["Spearphishing", "Living off Land"],
    "tools_used": ["Cobalt Strike", "WellMess"]
  }
}

Relationship 2: Report → Related Indicators

Why Embedding was NOT used:
Indicators are continuously updated with real-time sightings, confidence score shifts, and revocation flags. Embedding static indicator copies inside published reports would lead to data obsolescence and inconsistency.

Embedded Alternative Schema: 
{
  "report_id": "rpt-001",
  "title": "APT29 European Campaign",
  "indicators": [
    { "type": "ipv4-addr", "value": "194.165.16.11", "severity": "critical" },
    { "type": "domain-name", "value": "cdn-microsoftonline.net", "severity": "critical" }
  ]
}

3. Document Size Analysis ($bsonSize) & 16 MB Limit Verification

We run the MongoDB $bsonSize aggregation pipeline across the collection: 

db.indicators.aggregate([
  { $project: { doc_size: { $bsonSize: "$$ROOT" } } },
  { $group: { _id: null, avgSize: { $avg: "$doc_size" }, maxSize: { $max: "$doc_size" } } }
])
Verification Results from Live MongoDB Dump:
  • Average Document Size: ~1,340 bytes (1.31 KB)
  • Maximum Document Size: 1,589 bytes (1.55 KB)
  • MongoDB Hard BSON Limit: 16,777,216 bytes (16.00 MB)
  • Headroom Available: 16,775,627 bytes (>99.990% safe margin)
  • Conclusion: No documents remotely approach the 16 MB limit under this hybrid schema.
Activity for 7.1: Try It Yourself — Schema Redesign & Trade-Offs Experiment Analysis

Experiment: We redesigned the referencing relationship between indicators and threat_actors by embedding a summarized threat actor dossier directly inside the indicator’s attribution object.

What Queries Become FASTER:

  • SIEM Single-Lookup Triage: A firewall log check (db.indicators.findOne({ value: "185.220.101.47" })) retrieves the indicator, threat score, actor identity, country, and TTPs in one single network round-trip without requiring a $lookup join.
  • Working Set Cache Locality: Indicator data and actor metadata reside on the exact same WiredTiger memory page, eliminating auxiliary page cache misses.

What Queries Become HARDER / SLOWER:

  • Actor Profile Maintenance (Write Amplification): Updating an actor’s aliases or tools requires a multi-document update touching 10,000+ indicators instead of updating a single document in threat_actors.
  • Inconsistency & Partial Failures: Network glitches during mass updates cause stale intelligence across half the indicator records.
  • WiredTiger Cache Bloat: Duplicated actor strings consume valuable cache memory that could otherwise store active indicators.

Working Set Analysis & WiredTiger Cache Fit

1. Ingestion of 100,000 Documents (~2 KB Each)

Modeled on the awesome-annual-security-reports dataset, we ingested 100,000 telemetry documents (~2 KB each) into security_reports_working_set:

Metric Observed Value Engineering Implication
Document Count 100,000 documents Simulates enterprise security incident event logging
Uncompressed Data Size 206.31 MB Average document size is 2,048 bytes (2.0 KB)
WiredTiger On-Disk Size 6.41 MB Snappy block compression achieved a 32.16x compression ratio
Total Index Size 1.96 MB Indexes on report_id (unique) and threat_category
Total Active Working Set ~208.27 MB Data + Indexes required in RAM for active working set

2 & 3. WiredTiger Cache Metrics & Random Reads Simulation

Inspecting db.serverStatus()["wiredTiger"]["cache"] reveals the cache sizing algorithm:

Cache Allocation Formula:

Cache Max = max(50% of (RAM - 1GB), 256MB)
On this host: 7,879,000,064 bytes (7.34 GB)

Random Reads Benchmark (2,000 queries):

  • Execution Time: 0.778 seconds (2,571 queries/sec)
  • Average Query Latency: 0.389 ms
  • Observed Cache Hit Ratio: 98.17%

Conclusion: Since the active working set (~208 MB) is significantly smaller than the allocated WiredTiger cache (7,514 MB), data pages reside entirely in memory with near-zero disk evictions.
